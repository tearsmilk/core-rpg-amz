# core_weapons (武器) — эффекты кастомного оружия Nexo

Перенос Java-системы `core-weapons` на Python. Это Python-система внутри core-python, отдельной системой в `/pl` она
не видна. Поведение, команда, право, ключи PDC, строки `custom_model_data` и формат `config.yml` те же, что у Java-версии
(файл здесь — копия продового `systems/core-weapons/config.yml`). Описание поведений — в `core-weapons/README.md`.

| Файл | Что внутри |
|---|---|
| `main.py` | события, `/cweapons`, загрузка и выгрузка |
| `mochinushi.py` | игрок: замах (кадры `cw_swing_N`, огненный след) и кольцо частиц (`orbit`) |
| `jishin.py` | дрожь земли при крите (копии блоков `BlockDisplay`) |
| `dougu.py` | классы Java, id оружия (`nexo:id`, `coreweapons:id`), кадр на предмете, задачи для выгрузки |
| `settei.py`, `ronri.py` | чистая логика: разбор конфига, кадры, строки, геометрия |
| `tests_core_weapons.py` | тесты чистой логики: `python3 tests_core_weapons.py` |

`/cweapons give <оружие> [игрок] | list | reload` (алиас `/coreweapons`), право `coreweapons.admin`. Если Java-система
`core-weapons` ещё включена, команда занята. Тогда она доступна как `/py-core_weapons:cweapons`, а события
обрабатываются дважды. Перед загрузкой этой системы Java-систему нужно выключить: `amazake system disable core-weapons`.

## Чем отличается от Java (ради интерпретатора GraalPy)

- Постоянной задачи «каждый тик на каждого игрока» нет. Задача замаха (1 тик) живёт 6 тиков после взмаха. Задача
  кольца живёт, пока оружие с `orbit` в руке. Если `orbit` не включён ни у одного оружия (как у косы на проде),
  периодических задач у игроков нет совсем. Если включён, кольцо запускается сразу при смене слота хотбара. Если
  предмет попал в руку иначе (подобран, переложен), кольцо появится в течение 10 тиков: столько ждёт наблюдатель.
- Столбцы волны дрожи считаются заранее. Каждый тик дрожи трогает только те копии блоков, которым пора подняться,
  опуститься или исчезнуть.
- Выгрузка: после `@on_unload` контекст Python закрывается. Поэтому кадр с предмета игрока из чужого потока и копии
  блоков в чужом регионе снимает планировщик сущности чистым Java-объектом (`java.beans.Statement` +
  `EventHandler`). В своём потоке это делается сразу. Кадр снимается с самого стека, на котором он стоит, а не со
  слота, поэтому чужой предмет не затрётся. Остатки после сбоя снимаются при входе и при загрузке, как в Java.
- `PlayerArmSwingEvent` клиент шлёт каждый тик, пока игрок держит атаку по блоку. Это один вызов Python (~0,1–0,3 мс)
  на копающего игрока за тик. Обработчик выходит сразу при копании, до чтения предмета, но сам вызов остаётся: событие
  — единственный признак взмаха.
- Откат `min-interval` и тик начала замаха считаются по `Bukkit.getCurrentTick()`, а в Java — по счётчику задачи
  игрока, которая шла каждый тик. Постоянной задачи здесь нет. Пока регион не отстаёт, счёт тот же. Удержание
  первого кадра (`swingFresh`) — флаг, как в Java: если задача замаха уже идёт, её следующий запуск кадр не двигает.
  Новая задача стартует через тик, и эта задержка и есть удержание.
- Задача кольца запускается с `period` оружия. Если `period` сменился (другое оружие, `/cweapons reload`), задача
  перезапускается с новым.

## Защита от двойной работы

Amazake регистрирует команды систем и под префиксом имени системы. Если при загрузке в карте команд есть
`core-weapons:cweapons`, значит включена Java-система `core-weapons`. Тогда эта система «спит»: игроков не ведёт, дрожь
не запускает и пишет предупреждение в лог. Кому достанется сама `/cweapons`, зависит от порядка включения, поэтому
команда этой системы может быть только `/py-core_weapons:cweapons`. После `amazake system disable core-weapons`
достаточно `/py-core_weapons:cweapons reload` (или `/python reload core_weapons`), и эффекты включатся. Проверка идёт
только при загрузке и при `reload` во сне: если Java-систему включить, когда эта уже работает, обе будут работать.

## Известные отличия, которые из скрипта не исправить

- Автодополнение делает хост core-python (`PyCommand.tabComplete`). Без права `coreweapons.admin` подсказок нет: в
  Java права не проверялись, но Brigadier и так скрывает команду. Каждый аргумент фильтруется по началу без учёта
  регистра: в Java — только первый. Подсказок не больше 200.
- Выгрузка. В Java у каждого игрока в его потоке снимались кадры со всего инвентаря и с курсора. Здесь — только у
  тех, кто посреди замаха: другим неоткуда взять кадр этого запуска. В своём потоке кадры снимаются со всего
  инвентаря и с курсора. Из чужого потока снимается только кадр с живого стека, на котором он стоял. Курсор не
  проверяется. Если в этот же тик предмет разделили или взяли на курсор, кадр останется до следующего входа или
  загрузки, где хвосты снимаются (как в Java после сбоя).
- Для задач уборки при выгрузке нужен `Plugin` (планировщик сущности). В API `amazake` его нет, поэтому он берётся
  отражением через закрытые поля хоста (`ScriptApi.script` → `PyScript.platform` → `BukkitPlatform.context.plugin()`).
  Если не вышло, в лог пишется предупреждение и берётся первый включённый плагин. Правильнее было бы добавить в хост
  API вроде `amazake.plugin()` или «Java-задачи после выгрузки».

При тестах запускайте `python3 -B tests_core_weapons.py`, чтобы не появлялась папка `__pycache__`.
